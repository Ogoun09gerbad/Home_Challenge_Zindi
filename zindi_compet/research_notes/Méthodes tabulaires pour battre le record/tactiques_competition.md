## Quelles techniques de pseudo-labeling / apprentissage semi-supervisé sont documentées comme efficaces en 2025-2026 sur du tabulaire à cible rare, et avec quelles précautions ?

### Takeaway
Le pseudo-labeling reste une technique standard chez les Grandmasters Kaggle en 2025-2026 (formalisée dans le "Kaggle Grandmasters Playbook" de NVIDIA), avec trois précautions documentées : (1) utiliser des labels probabilistes/soft plutôt que durs, (2) recalculer les pseudo-labels par pli en K-Fold pour éviter la fuite de validation, (3) terminer par un fine-tuning sur les labels originaux uniquement. Sur Zindi, la légalité de cette pratique est explicitement contestée et dépend du règlement exact de chaque compétition — le staff Zindi a par le passé interdit l'usage du test set pour construire un modèle, menaçant de disqualifier la solution gagnante.

### Cited Findings
- Le "Kaggle Grandmasters Playbook" (NVIDIA Developer Blog, co-écrit par Chris Deotte, Kazuki Onodera, Théo Viel, Mrigendra Agrawal) décrit le pseudo-labeling comme : entraîner un modèle "Level 0", l'utiliser pour prédire des labels sur des données non labellisées (test set ou données externes), puis entraîner un modèle "Level 1" sur l'union des données originales + pseudo-labellisées — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Le même article formule le principe : "The stronger the model, the better the pseudo-labels" (plus le modèle enseignant est fort — notamment via ensembles ou plusieurs rounds — meilleurs sont les pseudo-labels) — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Recommandation explicite d'utiliser des probabilités (soft labels) plutôt que des labels durs 0/1, afin de réduire le bruit introduit et de permettre de filtrer les échantillons à faible confiance — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Les pseudo-labels peuvent servir de pré-entraînement, suivi d'un fine-tuning final sur les données originales labellisées uniquement (dernière étape du pipeline) — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Précaution anti-fuite explicite : "if you use K-Fold or Nested K-Fold, you can make this generalize better and avoid leakage" — autrement dit, il faut calculer K jeux de pseudo-labels (un par pli), pour que les données de validation d'un pli ne reçoivent jamais de pseudo-labels issus d'un modèle qui les a vues — [Blog NVIDIA, Chris Deotte, stacking cuML](https://developer.nvidia.com/blog/grandmaster-pro-tip-winning-first-place-in-a-kaggle-competition-with-stacking-using-cuml/)
- BirdCLEF 2024 (exemple cité dans le playbook, hors tabulaire mais même logique) a utilisé des soft pseudo-labels sur des clips audio non labellisés pour améliorer la généralisation à de nouvelles espèces/conditions d'enregistrement — aucun chiffre donné — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Les pseudo-labels peuvent aussi servir à repérer des échantillons d'entraînement bruités (labels douteux), par exemple là où plusieurs modèles sont en désaccord — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Sur Zindi, le staff officiel a explicitement interdit (au moins dans une compétition, SDG Text Classification Challenge) l'usage du test set pendant l'entraînement : "please note that you should not use the test set to help build your model! Bring in the test data only at the end to generate your submission", avec menace de retirer une solution gagnante qui le ferait — [Discussion Zindi SDG](https://zindi.africa/competitions/sustainable-development-goals-sdgs-text-classification-challenge/discussions/38)
- Dans une autre compétition Zindi (Gender-Based Violence Tweet Classification Challenge, 2021), un compte modérateur répond que l'usage du test set n'est pas contraire au règlement et que "pseudo labeling is a technique widely used in data science competitions" — mais un autre intervenant dans le même fil qualifie cela de "cheating" ("ne pas utiliser le test set, c'est de la triche") — contradiction non résolue dans le fil, signe que la règle dépend fortement du règlement spécifique de chaque challenge — [Discussion Zindi GBV](https://zindi.africa/competitions/gender-based-violence-tweet-classification-challenge/discussions/9122)

### Inferences
- Pour la compétition cible (85/15, bagging 10 plis × 7 seeds déjà en place), la précaution "K pseudo-label sets par pli" est directement compatible avec l'infrastructure CV déjà existante : il suffirait de générer les pseudo-labels de test à l'intérieur de chaque pli d'entraînement (pas un seul passage global), pour éviter que l'incertitude des pseudo-labels ne soit optimiste.
- Étant donné le ratio 85/15 et la cible logloss/AUC combinée, un pseudo-labeling agressif sur les points de test proches de 0.5 (zone d'incertitude) est risqué : ces points sont justement ceux où le bruit gaussien de label documenté dans le contexte pourrait dominer, donc le gain net de pseudo-labeling pourrait être faible ou négatif si mal filtré par confiance.
- Avant d'investir dans cette technique, il est impératif de relire le règlement exact de la compétition Zindi visée (pas trouvé dans cette recherche) : le fil SDG montre que Zindi a historiquement sanctionné cette pratique dans certains challenges, alors qu'un autre fil la tolère. C'est un point de vigilance réglementaire, pas juste technique.

### Gaps
- Aucun write-up Zindi 2025-2026 documentant un gain chiffré de pseudo-labeling sur une compétition binaire tabulaire à cible rare n'a été trouvé.
- Aucune source ne quantifie le risque de sur-ajustement au leaderboard public via du pseudo-labeling itératif (c.-à-d. re-soumettre pour affiner les pseudo-labels en fonction du score public) — point que le contexte du problème soupçonne explicitement (rangs 1 et 3 avec AUC identique au 6e chiffre). Rien trouvé sur ce mécanisme précis en 2025-2026.

## Quelles techniques de stacking/blending de niveau 2 ont montré un gain net documenté récemment ?

### Takeaway
La source la plus documentée (le Kaggle Grandmasters Playbook, 2025) décrit deux techniques au-delà du blend pondéré simple : le **hill climbing / forward selection with replacement** (équivalent à Caruana et al. 2004) pour choisir les poids d'un blend par sélection gloutonne, et le **stacking à plusieurs niveaux** où les prédictions out-of-fold (OOF) de modèles de niveau 1 deviennent des features d'un modèle de niveau 2 (GBDT + NN recommandés en parallèle), avec un niveau 3 qui moyenne les sorties du niveau 2. Un gagnant de mars 2026 a poussé cette logique à 4 niveaux et 150 modèles sélectionnés parmi 850 expériences.

### Cited Findings
- **Hill climbing** : partir du meilleur modèle individuel, ajouter itérativement d'autres modèles avec des poids différents, ne garder que les combinaisons qui améliorent la validation, répéter jusqu'à stagnation ; l'accélération GPU (CuPy) permet d'évaluer des milliers de combinaisons de poids en parallèle (RMSE/AUC vectorisés) — [NVIDIA Developer Blog, Playbook](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Le gagnant de la compétition "Calorie Expenditure" (citée dans le playbook) a blendé XGBoost, CatBoost, réseaux de neurones et modèles linéaires avec cette méthode de hill climbing — [NVIDIA Developer Blog, Playbook](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- Chiffre concret cité : pour le challenge "Fertilizer", l'ensemble de 100 seeds XGBoost stabilise le score autour de 0.379 MAP@3, contre environ 0.376 pour la moyenne d'un seul seed — gain net d'environ +0.003 juste par agrégation de seeds, cohérent avec l'ordre de grandeur recherché dans le contexte de l'utilisateur — [NVIDIA Developer Blog, Playbook](https://developer.nvidia.com/blog/the-kaggle-grandmasters-playbook-7-battle-tested-modeling-techniques-for-tabular-data)
- **Stacking formalisé en 3 niveaux** (solution gagnante "Podcast Listening Time", Playground series, par Chris Deotte) : Level 1 = modèles divers (GBDT, NN, SVR, KNN, Random Forest, MLP, TabPFN, XGBoost, LightGBM — jusqu'à 75 modèles choisis parmi 500 expériences) ; Level 2 = modèles entraînés sur les prédictions OOF du Level 1 comme features, sélectionnées par **forward feature selection**, avec features dérivées comme `confidence = std(OOF)` et `consensus = mean(OOF)` ; recommandation d'avoir au moins deux familles de modèles au Level 2 (un GBDT et un NN) ; Level 3 = moyenne pondérée des sorties du Level 2 — [NVIDIA Developer Blog, stacking cuML](https://developer.nvidia.com/blog/grandmaster-pro-tip-winning-first-place-in-a-kaggle-competition-with-stacking-using-cuml/)
- Résultat de cette solution : RMSE de validation croisée 11.54 vs RMSE leaderboard privé 11.44 (écart faible, cohérent entre CV et private LB) — [NVIDIA Developer Blog, stacking cuML](https://developer.nvidia.com/blog/grandmaster-pro-tip-winning-first-place-in-a-kaggle-competition-with-stacking-using-cuml/)
- Évolution plus récente (compétition Playground, mars 2026, churn télécom scoré en AUC) : solution gagnante = **stack à 4 niveaux, 150 modèles sélectionnés parmi 850 expériences**, construite par des agents LLM (GPT-5.4 Pro, Gemini 3.1 Pro, Claude Opus 4.6) suivant le workflow du Playbook (EDA → baselines → feature engineering → hill climbing → stacking), plus de 600 000 lignes de code générées — [NVIDIA Developer Blog relayé par blockchain.news / Quantum Zeitgeist](https://quantumzeitgeist.com/nvidia-agents-kaggle-competition-generate/)
- La méthode de **sélection gloutonne avec remplacement** ("greedy forward selection with replacement", équivalente à Caruana et al. 2004, "Ensemble Selection from Libraries of Models") fonctionne ainsi : partir du modèle individuel au meilleur score ; à chaque tour, pour chaque candidat, former une moyenne à poids égaux (ensemble courant + candidat), ne garder le candidat que s'il améliore le score ; le même modèle peut être sélectionné plusieurs fois (équivalent à de l'optimisation de poids) ; le poids final d'un modèle = son nombre de sélections / nombre total de tours — nécessite au moins 3 modèles OOF divers en entrée — [SKILL.md claudskills.com, citant Caruana et al. 2004 et le Kaggle Grandmasters Playbook](https://claudskills.com/skills/kaggle-hill-climbing/SKILL.md)
- Un raffinement ultérieur recommandé : après la sélection gloutonne, affiner les poids par Nelder-Mead (scipy) sur le sous-ensemble retenu uniquement, avec poids normalisés en valeur absolue — et passer à Optuna (TPE, 500 essais) si plus de 5-8 modèles, car Nelder-Mead devient lent — [SKILL.md claudskills.com](https://claudskills.com/skills/kaggle-hill-climbing/SKILL.md)
- Pièges documentés pour l'optimisation de poids : un poids > 0.8 sur un seul modèle signifie qu'on ne blend pas vraiment (ajouter plus de diversité) ; optimiser les poids sur tout l'OOF sans un holdout séparé mène à un léger sur-ajustement au bruit de l'OOF ; ignorer la corrélation entre modèles tue le bénéfice de l'ensemble ; faire l'optimisation de poids avant la sélection gloutonne piège dans un optimum local en haute dimension — [SKILL.md claudskills.com](https://claudskills.com/skills/kaggle-hill-climbing/SKILL.md)
- Pour une métrique composite personnalisée (type 0.4×AUC + 0.6×(1−logloss/const)), aucune source trouvée ne documente cette pratique précise, mais les outils génériques (nyaggle `averaging_opt`, nommé explicitement compatible avec une fonction d'évaluation arbitraire et un indicateur `higher_is_better`) permettent en principe de passer n'importe quelle métrique, y compris composite, à une optimisation SLSQP des poids — [nyaggle docs](https://nyaggle.readthedocs.io/en/stable/source/reference/ensemble.html)

### Inferences
- Le pipeline déjà en place (LightGBM + CatBoost additifs + GAM P-splines, blend pondéré sur l'échelle probit, bagging 10×7) est au niveau "Level 1 + blend pondéré simple" de cette hiérarchie. Le gain documenté qui reste accessible et non encore exploité serait d'ajouter un Level 2 explicite entraîné sur les OOF (plutôt qu'un blend pondéré figé), ou de remplacer le blend pondéré simple par une sélection gloutonne (hill climbing) sur l'échelle probit, qui a montré des gains de l'ordre de +0.003 dans un cas documenté (Fertilizer : 0.376 → 0.379) — un ordre de grandeur comparable à l'écart recherché (0.741727 → 0.744434).
- Le risque principal signalé par la littérature (poids > 0.8 sur un modèle, optimiser sans holdout séparé de l'OOF) est pertinent ici car le nombre de modèles de base combinés (LightGBM, CatBoost, GAM) est faible (3), donc la sélection gloutonne ou le hill climbing a peu de marge pour apporter de la diversité réelle — le gain principal viendrait plutôt de la diversité intra-famille (seeds, profondeurs d'arbres additifs différentes) déjà exploitée par le bagging.
- Optimiser directement les poids de blend sur la métrique composite exacte de la compétition (au lieu d'optimiser AUC et logloss séparément puis blend naïf) est une piste défendable et peu risquée réglementairement (pas de données externes), mais non confirmée par un write-up spécifique — à tester en interne avec prudence (holdout séparé pour éviter le sur-ajustement signalé ci-dessus).

### Gaps
- Aucun write-up ne documente un stacking de niveau 2 appliqué spécifiquement à une métrique composite AUC/logloss pondérée (0.4/0.6) — l'inférence ci-dessus n'est pas confirmée empiriquement par une source.

## Comment les Grandmasters exploitent-ils en 2025-2026 la nature synthétique/quota d'un jeu de données (reverse engineering du générateur, duplicatas train/test, ID de session) ?

### Cited Findings
- Whitehill (article "Climbing the Kaggle Leaderboard by Exploiting the Log-Loss Oracle") démontre qu'un concurrent peut utiliser un oracle de score (le score public retourné après soumission) pour inférer par lots les labels du test set, sans entraîner de classifieur — appliqué à une compétition Kaggle de 2017 (Intel & MobileODT), permettant d'atteindre le rang #4 sans modèle — [arXiv/ar5iv](https://ar5iv.labs.arxiv.org/html/1707.01825)
- Une revue pédagogique du "leaderboard probing" le présente comme une technique liée à une fuite de données propre à la compétition : certains exploits permettent de récupérer tous les labels du leaderboard public, d'autres seulement la distribution des labels — [Tutoriel mlcourse.ai](https://nbviewer.jupyter.org/github/Dene33/mlcourse.ai/blob/master/jupyter_english/tutorials/kaggle_leaderboard_probing_nikolai_timonin.ipynb)
- Un fil de discussion Zindi (compétition différente de celle visée) mentionne que des concurrents ont "hardcodé des valeurs fuitées" et que le règlement ne l'interdit pas explicitement, même si la pratique "repousse les limites" — [Discussion Zindi, citée via recherche indirecte, compétition non précisée]
- La Tabular Playground Series (Kaggle, lancée en 2021, antérieure à 2025) utilisait des données synthétiques générées par un réseau génératif profond (CTGAN) à partir de données réelles — information historique, pas 2025-2026, mais confirme que le principe "générateur réutilisé" est une pratique connue et documentée côté Kaggle depuis plusieurs années — [Packt, The Kaggle Book](https://packt-plus-non-live.prod.packtpub.com/en-at/product/the-kaggle-book-9781801817479/chapter/modeling-for-tabular-competitions-9/section/the-tabular-playground-series-ch09lvl1sec47)
- Un forum DrivenData (plateforme différente de Kaggle/Zindi) rapporte un cas communautaire (non analysé formellement) de lignes dupliquées dans le jeu de test, certaines avec des valeurs de cible différentes pour les mêmes features — rapport communautaire seulement, pas une analyse formelle confirmée — [Forum DrivenData](https://community.drivendata.org/t/there-are-duplicate-rows-in-the-test-data/55)

### Inferences
- L'hypothèse de l'utilisateur (rangs 1 et 3 partageant une AUC identique au 6e chiffre malgré 1 et 25 soumissions respectivement) est structurellement cohérente avec un scénario de type "oracle de score" ou de partage de prédictions entre comptes (plutôt qu'un apprentissage itératif supérieur), par analogie avec le mécanisme documenté par Whitehill en 2017 — mais cette analogie reste une inférence de l'agent de recherche, non une confirmation d'un cas similaire en 2025-2026. ## Quelles techniques de calibration / optimisation directe pour métriques composites (logloss + AUC) sont recommandées au-delà de Platt/isotonic ?

### Takeaway
Aucune source 2025-2026 ne documente une méthode de calibration spécifiquement conçue pour une métrique composite AUC+logloss pondérée. La littérature académique récente (2025) propose des méthodes de calibration plus fines que Platt/isotonic (ex. "clustered calibration" par sous-populations apprises), mais sans lien établi avec des compétitions de ce type ; la pratique de compétition documentée reste : optimiser le ranking (AUC) via le modèle, puis calibrer séparément pour la composante logloss, en évaluant le compromis sur les OOF.

### Cited Findings
- Un article récent (octobre 2025, arXiv) intitulé "Clustered Calibration: Representation-Aware Probability Calibration via Learned Subpopulations" (Lavi, Shapira, Rappoport) propose une calibration par sous-population apprise plutôt qu'une calibration globale (Platt/isotonic) — le texte complet n'a pas pu être extrait automatiquement (PDF non décodable par l'outil de fetch), seuls les métadonnées et la liste de sections (Introduction, Benchmarks and Related Work, Calibration Methods, Method, annexe théorique) ont pu être confirmés ; les références citent des jeux de données tabulaires de classification binaire (Adult, diabetes 130-US hospitals, Default of Credit Card Clients), suggérant une applicabilité probable au même type de problème, mais ceci reste une inférence à partir des citations, non un résultat confirmé — [arXiv 2510.19328](https://arxiv.org/pdf/2510.19328)
- Un article plus ancien mais fondamental sur la "field-aware calibration" rappelle que l'AUC est indépendante du seuil et insensible à l'échelle des prédictions, ce qui justifie le pattern "optimiser le ranking avec AUC, puis corriger la calibration séparément (Platt/isotonic) pour améliorer le logloss sans changer le ranking" — [arXiv 1905.10713](https://arxiv.org/pdf/1905.10713)
- Des bibliothèques génériques d'optimisation de poids de blend (nyaggle `averaging_opt`, Endgame `OptimizedBlender`) acceptent une fonction de métrique arbitraire (pas seulement AUC ou logloss seuls) et un indicateur de sens (maximiser/minimiser), ce qui permet en principe de passer directement la formule composite de la compétition comme objectif d'optimisation des poids de blend plutôt que d'optimiser AUC et logloss séparément — [nyaggle docs](https://nyaggle.readthedocs.io/en/stable/source/reference/ensemble.html) ; [Endgame docs](https://endgame-ml.readthedocs.io/en/latest/guides/ensembles.html)

### Inferences
- Étant donné que Platt/isotonic ont déjà été testés et rejetés par l'utilisateur, et qu'aucune alternative "compétition" plus avancée n'a pu être confirmée dans la littérature 2025-2026, la piste la plus solidement documentée qui reste réellement nouvelle est d'arrêter de traiter calibration et ranking séparément, et d'optimiser directement les **poids du blend final sur la métrique composite exacte** (0.4×AUC + 0.6×(1−logloss/0.595)) via une recherche de poids (scipy/Optuna) sur les prédictions OOF probit-transformées déjà produites — cela ne nécessite aucune nouvelle méthode de calibration per se, mais change l'objectif d'optimisation du blend lui-même. C'est une inférence de bon sens combinant les éléments trouvés (outils génériques + principe ranking/calibration séparés), pas une tactique confirmée par un write-up dédié à ce problème précis.
- La "clustered calibration" (si son contenu complet confirme l'applicabilité au tabulaire binaire) pourrait être pertinente si le bruit de label gaussien mentionné dans le contexte affecte différemment des sous-populations identifiables (ex. certaines plages de features) — mais ceci reste spéculatif tant que le papier n'a pas pu être lu en détail.

### Gaps
- Le contenu complet et les résultats numériques (gains de logloss/AUC rapportés) de l'article "Clustered Calibration" n'ont pas pu être extraits (échec de décodage PDF par l'outil de fetch) — à relire manuellement via https://arxiv.org/abs/2510.19328 si cette piste est jugée prometteuse.
- Aucune source ne documente une technique de calibration "post-Platt/isotonic" spécifiquement éprouvée en compétition (Kaggle ou Zindi) 2025-2026 sur une métrique composite de type AUC+logloss.
- Aucun write-up ne confirme empiriquement qu'optimiser les poids de blend directement sur la métrique composite (plutôt que sur AUC ou logloss séparément) apporte un gain net documenté en compétition — c'est une inférence d'outillage générique, pas un résultat cité.

## Y a-t-il des techniques de noise injection / label smoothing / perturbation ciblée connues pour aider quand le bruit de label est confirmé gaussien ?

### Takeaway
Aucune source 2025-2026 ne documente de technique de noise injection ou label smoothing appliquée à une compétition tabulaire avec bruit de label gaussien confirmé. La littérature académique disponible montre que le label smoothing est mathématiquement équivalent à une injection de bruit symétrique sur les labels et peut rivaliser avec des méthodes de correction de perte sous bruit de label, mais ces résultats proviennent de recherche générale (vision/texte), pas de compétitions tabulaires récentes, et aucun lien direct avec le cas précis (bruit gaussien plutôt que symétrique catégoriel) n'a été établi.

### Cited Findings
- Lukasik et al. (ICML 2020, "Does label smoothing mitigate label noise?") montrent que le label smoothing agit comme une injection de bruit symétrique sur les labels, et qu'il peut égaler des méthodes de correction de perte dédiées sous bruit de label ; ils trouvent aussi qu'adoucir (smooth) le modèle enseignant aide spécifiquement en distillation à partir de données bruitées — [Google Research](https://research.google/pubs/does-label-smoothing-mitigate-label-noise/)
- Eisenbürger et al. (2024/2025) adaptent des méthodes de détection/correction de bruit de label pour les modèles à base d'arbres boostés (GBDT), avec plus de 99% de précision de détection de bruit sur le jeu Adult, mais des gains de performance après correction variables selon le jeu de données — [alphaXiv 2409.08647](https://www.alphaxiv.org/overview/2409.08647)
- Une étude ICML 2025 injecte du bruit de label de 0% à 30% sur 15 jeux OpenML binaires et compare la robustesse de TabPFN à 7 classifieurs classiques (random forest, XGBoost, LightGBM, SVM, kNN, CatBoost, arbres de décision) — [ICML 2025](https://icml.cc/virtual/2025/47490)
- Un article plus ancien (Automunge, 2022) sur la perturbation stochastique de features tabulaires note que le bruit de label est un cas particulier du bruit de features, et qu'une injection intentionnelle de bruit de label peut aider à compenser un bruit de label inhérent déjà présent (citant Chen et al. 2021) — mais ceci concerne principalement le bruit de features, pas le bruit de label gaussien spécifiquement — [ar5iv, Automunge](https://ar5iv.labs.arxiv.org/html/2202.09248)
- Kim et al. (Machine Learning Journal, 2025) étudient l'impact du bruit de label sur la génération de données tabulaires synthétiques : qualité et utilité se dégradent avec le niveau de bruit croissant, sans effet significatif sur la convergence du générateur — pertinent pour comprendre le générateur synthétique sous-jacent, mais pas une tactique de compétition — [mlanthology.org](https://mlanthology.org/mlj/2025/kim2025mlj-empirical)

### Inferences
- Si le bruit de label est confirmé gaussien (continu) plutôt que catégoriel/symétrique, les résultats de Lukasik et al. (label smoothing = bruit symétrique sur labels catégoriels) ne s'appliquent pas directement : un bruit gaussien sur une cible binaire suggère plutôt que le label observé est une version bruitée d'une probabilité latente continue — dans ce cas, la piste la plus défendable (mais non confirmée par une source de compétition) serait de traiter le problème comme une régression sur la probabilité latente plutôt que comme une classification à labels durs, ce qui recoupe la régularisation via soft/pseudo-labels déjà documentée en Q1. Ceci reste une inférence de l'agent, pas un résultat cité.
- Aucune preuve trouvée que l'injection de bruit gaussien ciblé sur les labels d'entraînement (dans le sens inverse, pour "matcher" le bruit du générateur) ait été testée ou documentée comme tactique de compétition — il s'agit d'un terrain non couvert par la littérature trouvée.

### Gaps
- Aucun write-up de compétition (Kaggle ou Zindi, 2025-2026) mentionnant explicitement une technique de noise injection ou label smoothing pour un cas de bruit de label gaussien confirmé n'a été trouvé.
- Le lien entre la littérature trouvée (toutes génériques, pré-2025 pour la plupart, ou académiques sans ancrage compétition) et le cas précis de l'utilisateur (bruit gaussien confirmé sur données synthétiques Zindi) reste spéculatif — à traiter avec prudence, aucune confirmation empirique disponible.
